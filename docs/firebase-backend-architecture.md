# Firebase Backend Architecture Plan

## 1. Overview
This document outlines the proposed Firebase backend architecture for the HyFePoul system. It bridges the ESP32 (acting as a Wi-Fi gateway for the Arduino Mega) and the React Native Mobile Application. 

The architecture strictly adheres to the finalized constraints in `docs/data-communication-contract.md` and `docs/mega-esp32-protocol.md`.

## 2. Firebase Project Structure
*   **Environments:** Two distinct Firebase projects are recommended: `HyFePoul-Dev` and `HyFePoul-Prod`.
*   **Local Testing:** The Firebase Local Emulator Suite (Auth, Firestore, Functions) will be used for rapid local development without cloud costs.
*   **Core Services:**
    *   **Cloud Firestore:** NoSQL database for users, devices, and historical system updates.
    *   **Firebase Authentication:** Email/password identity management.
    *   **Cloud Functions:** Serverless Node.js REST endpoints for ESP32 ingestion and event processing.
    *   **Cloud Messaging (FCM):** Push notifications for actionable events.

## 3. Firestore Collections and Schema
*   **`users/{uid}`**
    *   `email`: String
    *   `role`: String (e.g., "owner")
    *   `fcmTokens`: Array of Strings (for notifications)
*   **`devices/{deviceId}`**
    *   `ownerId`: String (UID)
    *   `esp32Status`: String (`"ONLINE"`, `"OFFLINE"`)
    *   `lastHeartbeat`: Timestamp
    *   `currentState`: Map (Holds the exact latest `DATA` fields)
*   **`devices/{deviceId}/systemData/{docId}`**
    *   Historical periodic snapshots of `DATA` payloads.
*   **`devices/{deviceId}/alerts/{alertId}`**
    *   Actionable event tracking (state, resolution, timestamps).

## 4. Required Fields & Data Types
The backend strictly enforces the fields defined by the Mega:
*   `feedWeightGrams`: Integer
*   `targetFeedGrams`: Integer
*   `hopperLevelPercent`: Integer (0-100)
*   `waterLow`: Boolean
*   `waterHigh`: Boolean
*   `pumpActive`: Boolean
*   `feedingActive`: Boolean
*   `emergencyStopActive`: Boolean
*   `timestamp`: String (UTC ISO 8601 `Z`)

## 5. Device Identification & Claiming
*   **Initial Provisioning:** The ESP32 is flashed with a static `deviceId`. This ID is pre-created in the Firestore `devices` collection.
*   **Claiming:** The user enters the `deviceId` in the mobile app. A Cloud Function validates the ID, sets the `ownerId` to the user's UID, and secures the device via Firestore Rules.

## 6. ESP32 → Firebase Communication
*   **Method:** HTTP POST requests to Firebase Cloud Functions REST API.
*   **Reasoning:** Direct ESP32-to-Firestore via native SDKs requires heavy OAuth/JWT overhead or insecure relaxed rules. Cloud Functions allow lightweight HTTPS with custom pre-shared key validation.

## 7. Authentication/Security for ESP32
*   **Method:** The prototype request authentication model utilizes HTTP Headers:
    *   `X-Device-ID: <deviceId>`
    *   `X-Device-Token: <device-secret>`
*   **Secret Management:** Firebase/Google Cloud Secret Manager with supported parameterized secrets will be used for ESP32 device secrets. The raw device secret must not be stored in a normal Firestore document and must never be included in the mobile application.
*   **Cloud Function Validation Flow:** The Cloud Function must:
    1. Identify the device via `X-Device-ID`.
    2. Verify the device secret (`X-Device-Token`).
    3. Verify the device is registered/enabled.
    4. Validate the request payload strictly.
    5. Only then write to Firestore.

## 8. Mobile App → Firebase Access
*   **Method:** Official Firebase JS SDK.
*   **Security:** Firestore Security Rules enforce that a user can only read/write devices where `ownerId == request.auth.uid`.

## 9. Cloud Functions Responsibilities
*   **`POST /device/data`**: Ingests periodic system status.
*   **`POST /device/event`**: Ingests actionable/informational events.
*   **`Scheduled Function (Cron)`**: Detects if `lastHeartbeat` is excessively stale, marking `esp32Status` as `"OFFLINE"`.

## 10. FCM Notification Architecture
1. Cloud Function receives an actionable event (e.g., `LOW_WATER`).
2. Function looks up the `fcmTokens` array in the `users` document associated with the device.
3. Function dispatches a localized Firebase Cloud Message to the Android device.

## 11. Alert Lifecycle and Deduplication
*   **Deduplication:** Cloud Functions cache or query recent `eventId`s (e.g., `42-1045` generated by the Mega). If an event arrives with an existing unresolved ID, it is dropped.
*   **Lifecycle:** An alert is created as `RESOLVED: false`. Subsequent `DATA` payloads are checked; if the condition normalizes, the Cloud Function marks the alert `RESOLVED: true`.

## 12. Data Retention Strategy
*   To prevent runaway Firestore storage costs, a scheduled Cloud Function will run nightly to prune `systemData` documents older than a defined limit (e.g., 30 days).

## 13. Firestore Read/Write Strategy & Quotas
*   **Write Optimization (Data Storage Strategy):** To prevent unnecessary high-frequency writes, data is stored as follows:
    *   Current state → `devices/{deviceId}`
    *   Meaningful events/alerts → `alerts` documents
    *   Periodic historical snapshots → `systemData`
*   **Transmission Interval:** The initial backend implementation will use a configurable DATA transmission interval for testing. The final transmission frequency will be determined during firmware and physical-system validation.
*   **Read Optimization:** The dashboard listens to a single `devices/{deviceId}` document to minimize document reads rather than querying historical `systemData`. (Note: Firestore real-time listener updates still count as document reads).

## 14. Offline/Device-Network Behavior
*   **ESP32 Offline:** Detected via missed backend heartbeats. Backend manages the `DEVICE_OFFLINE` alert.
*   **Mobile App Offline:** The mobile application may use Firebase offline caching capabilities for previously retrieved data. Remote device-control commands are not currently implemented and therefore are not queued or transmitted to physical hardware.

## 15. Error and Invalid-Data Handling
*   **Strict Rejection:** Mirroring the serial protocol, if a payload sent to the Cloud Function is missing fields or contains invalid types, the Cloud Function responds with `400 Bad Request` and discards the entire payload. No partial updates are allowed.

## 16. Development/Testing Environment
*   **Tools:** Firebase Local Emulator Suite.

## 17. Required Firebase Configuration/Secrets
*   **Backend:** Firebase/Google Cloud Secret Manager. No `functions.config()` or legacy runtime configuration will be used.

## 18. Deployment Process
*   **Backend:** Deployed via Firebase CLI.
*   **Mobile:** Built via Expo EAS.

## 19. Mobile App MockDataContext Migration
*   A new `FirebaseDataContext` will be created implementing identical TypeScript definitions. `App.tsx` will swap the provider. The UI screens will require **zero changes**.
